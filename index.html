CASE STUDY
Wholesale travel · Node.js · Express · React · PostgreSQL · Prisma · JWT

B2B Travel Portal

Built by me Client details confidential Production release not claimed

A role-based portal where a wholesale travel operator publishes packages and visa services to partner travel agencies, and each agency quotes its own customers at its own margin.

The problem

Wholesalers sell packages and visa services through partner agencies. Every agency needs its own markup and its own branded quotations, while the wholesaler's cost price and branding must not leak into what the agency's customers receive.

What I implemented

Express/Node.js REST APIs with JWT authentication and role-controlled operations; a React front end; a PostgreSQL schema managed through Prisma; agency-specific markup calculation; white-label PDF quotations; and the package and visa-request workflows.

Roles and data model

Three roles — admin, data-feeder and partner agency — each limited to its own operations. Packages and visa requests carry wholesale values; an agency's markup produces the price it quotes. Quotations store snapshots of price and itinerary at generation time, and records are soft-deleted rather than removed.

Engineering decisions

Historical snapshots, so editing a package later never rewrites a quotation already issued. Soft deletion, to keep past quotations and requests intact. Separate roles for the people who enter data, the people who sell, and the people who administer.

Edge cases and testing

Found and corrected a payment amount-due defect involving wholesale versus marked-up prices. Inspected generated quotation PDFs for unwanted wholesaler branding. Confirmed that historical quotation values are preserved through snapshots. These were hands-on reliability checks; no claim is made here about automated test coverage.

Verified delivery status

Approved for technical discussion. Not claimed: client acceptance, commercial operation, live payment processing, production release. Withheld: customer identities, pricing, contracts, screenshots and the private repository.

2026 · Python · FastAPI · PostgreSQL · MinIO

File Vault

Independent prototype Public repository

A multi-tenant file-service prototype. A control-plane registry tracks organisations; each organisation gets its own PostgreSQL database and its own MinIO bucket, selected by the organisation slug in the URL. Uploads stream to object storage with SHA-256 hashing, MIME checks and size limits. I verified data separation manually and diagnosed a schema-provisioning problem along the way.

Known limits, stated up front
  • No authentication or per-tenant authorization yet. Separate databases isolate stored data, but they do not stop a caller from naming another organisation's slug. This is not a production-secure SaaS.
  • No automated tests and no CI; separation was checked by hand.
  • The orphan-file cleanup script covers only the default bucket, not every organisation.
  • The repository README still describes the earlier single-tenant version.
